# Architecture

This document explains how the AI Agent Orchestration Dashboard is structured and how data moves through the system.

## System Overview

The project is split into a FastAPI backend and a React + TypeScript frontend.

```text
React Dashboard
  |
  | REST requests and Server-Sent Events
  v
FastAPI API
  |
  +--> SequentialOrchestrator
  |      +--> Specialized agents
  |      +--> OpenRouter-compatible model API
  |
  +--> WorkflowEventBus
  |      +--> SSE stream consumed by the frontend
  |
  +--> WorkflowRepository
         +--> SQLite tables for workflow runs and agent steps
```

The application is intentionally CPU-friendly. It calls hosted model APIs through HTTP and does not require local GPU inference.

### Responsibilities

- `agents/` defines role-specific model prompts and wraps model calls behind a common agent interface.
- `api/routes/` exposes HTTP endpoints for health checks, single-agent execution, full workflows, saved runs, and live events.
- `core/config.py` loads environment-driven settings with `pydantic-settings`.
- `db/` owns SQLAlchemy ORM models and database session setup.
- `models/` contains Pydantic domain models returned by the API.
- `repositories/` maps between domain models and SQLAlchemy records.
- `services/openrouter_client.py` handles outbound model API requests.
- `services/orchestrator.py` runs agents in order and builds workflow results.
- `services/workflow_events.py` stores and broadcasts workflow events for SSE clients.

## Agent Orchestration Flow

The backend currently uses a fixed sequential workflow.

```text
POST /api/workflows/run
  |
  v
SequentialOrchestrator.run(task)
  |
  +--> publish workflow_started
  +--> publish pending events for all agents
  |
  +--> Planner Agent
  |      input: original user task
  |      output: task breakdown
  |
  +--> Research Agent
  |      input: original task + planner output
  |      output: research/context
  |
  +--> Technical Architect Agent
  |      input: original task + previous outputs
  |      output: architecture proposal
  |
  +--> Developer Agent
  |      input: original task + previous outputs
  |      output: implementation guidance
  |
  +--> Reviewer Agent
  |      input: original task + previous outputs
  |      output: review notes and risks
  |
  +--> Final Answer Agent
         input: original task + previous outputs
         output: final response
```

For each agent, the orchestrator publishes:

1. `agent_running`
2. `agent_completed` or `agent_failed`

When the workflow finishes, it publishes:

1. `workflow_completed` for success
2. `workflow_failed` for failure

If an agent fails, later agents do not run. The orchestrator returns a failed workflow result with the completed steps and a workflow-level error message.

## Database Design

SQLite is used for local development and portfolio demonstration. The database is accessed through SQLAlchemy and can be replaced later with PostgreSQL without changing the API contract.

### `workflow_runs`

| Column | Purpose |
| --- | --- |
| `id` | Workflow identifier, generated by backend or supplied by client. |
| `original_task` | User task submitted to the workflow. |
| `status` | Workflow status: pending, running, completed, or failed. |
| `final_answer` | Final answer produced by the final answer agent. |
| `error` | Workflow-level error message, if any. |
| `created_at` | Run creation timestamp. |
| `completed_at` | Completion timestamp. |
| `duration_ms` | Total workflow duration in milliseconds. |

### `agent_execution_steps`

| Column | Purpose |
| --- | --- |
| `id` | Step identifier. |
| `workflow_id` | Foreign key to `workflow_runs.id`. |
| `position` | Step order inside the workflow. |
| `agent_role` | Agent role, such as planner or reviewer. |
| `name` | Human-readable agent name. |
| `description` | Agent responsibility summary. |
| `input` | Prompt/context sent to the agent. |
| `output` | Agent result. |
| `status` | Step status. |
| `error` | Step-level error message, if any. |
| `started_at` | Agent start timestamp. |
| `completed_at` | Agent completion timestamp. |
| `duration_ms` | Agent execution duration in milliseconds. |

The relationship is one workflow run to many agent execution steps. Step records are ordered by `position`.

## Frontend Dashboard Flow

The frontend is a Vite React application with a dashboard-style layout.

```text
Dashboard page
  +--> checks backend health

Workflow Run page
  +--> user submits a task
  +--> frontend generates workflow_id
  +--> frontend opens EventSource to /api/workflows/{workflow_id}/events
  +--> frontend posts task to /api/workflows/run
  +--> graph and cards update as SSE events arrive
  +--> final POST response is used as fallback

Workflow History page
  +--> reads GET /api/workflows
  +--> links to saved workflow details

Workflow Detail page
  +--> reads GET /api/workflows/{workflow_id}
  +--> renders persisted graph, final answer, and per-agent cards
```

### Key Frontend Modules

- `src/api/client.ts` configures the Axios base client.
- `src/api/workflows.ts` wraps health, workflow, and SSE URL helpers.
- `src/hooks/useWorkflowEvents.ts` manages the browser `EventSource` connection.
- `src/components/workflows/WorkflowGraph.tsx` renders the React Flow graph.
- `src/components/workflows/AgentStepCard.tsx` renders each agent result.
- `src/pages/WorkflowRunPage.tsx` coordinates task submission and live updates.
- `src/pages/WorkflowHistoryPage.tsx` and `WorkflowDetailPage.tsx` show persisted runs.

## API Surface

| Method | Endpoint | Responsibility |
| --- | --- | --- |
| `GET` | `/health` | Health metadata for dashboard and operational checks. |
| `POST` | `/api/agents/planner/run` | Run the planner agent by itself. |
| `POST` | `/api/workflows/run` | Run the complete sequential workflow. |
| `GET` | `/api/workflows` | Return saved workflow runs. |
| `GET` | `/api/workflows/{workflow_id}` | Return one saved workflow and its steps. |
| `GET` | `/api/workflows/{workflow_id}/events` | Stream live workflow events. |

## Testing Strategy

Backend tests cover:

- API health and OpenAPI contract.
- Base agent success and failure behavior.
- Specialized agent prompt wiring.
- Sequential orchestration order, context passing, and failure stops.
- Workflow persistence through repository and API routes.
- SSE event formatting and event bus replay behavior.
- Pydantic model defaults and validation.
- OpenRouter client behavior with mocked HTTP calls.

Frontend tests cover pure display helpers used by dashboard cards and workflow views. This keeps the initial test setup fast and practical while leaving room for component tests later.

## Runtime And Deployment Notes

- Local development can run directly with Python and npm or through Docker Compose.
- Docker Compose bind-mounts source code for quick iteration.
- The backend container exposes port `8000`.
- The frontend container exposes port `5173`.
- SQLite data in Docker is stored in the `backend_data` volume.
- The project does not configure GPU runtime and sets `CUDA_VISIBLE_DEVICES` to an empty value in Compose.

## Future Architecture Improvements

1. Add parallel agent execution for independent steps.
2. Add conditional branching based on agent outputs.
3. Move long-running workflows to a background worker and queue.
4. Add PostgreSQL support for multi-user deployments.
5. Add authentication, teams, and project workspaces.
6. Add richer event replay and resumable workflow state.
7. Add integration tests that exercise frontend and backend together.
